What 63C-4 settles

Where it plugs in: the stack decision record’s “login method” item, and the per-FN authorization line for any FN that opens a session from an assertion.

1. Account linking and takeover (the big one).

Identify the subscriber by issuer + subject together, and never process the subject alone (§3.4, §4.9).
Linking needs an existing authenticated session, and should require authenticating with an already-linked identifier first (§3.8.1).
Removing an identifier must revoke access through it. The user must be notified on every add or remove (§3.8).
Account resolution (matching an incoming identity to an existing account by attributes) must use attributes that resolve uniquely, and must never attach data to an identifier that doesn’t belong to the subscriber (§3.8.2).
The spec doesn’t say “never auto-link on email match”, but §3.8.2 implies it. email_verified is an OIDC claim, not a NIST one, so wings adds it as its own rule. Link by email only after an authenticated session proves control of the existing account.

2. A session is created only when all five conditions hold (§3.9):

A valid assertion was processed.
It came from the expected IdP.
That IdP matches the issuer in the federated identifier.
It maps to a provisioned RP account.
The account was provisioned the way the trust agreement says.

This reads as a ready-made checklist for the login-callback FN.

3. Assertion validation list (§4.9). Seven checks, in order:

Signature, with a key belonging to the IdP
Issuer
Time window
Audience
Nonce
Acceptable assurance levels
Replay, via the assertion identifier

For OIDC this maps onto the ID Token claims and the checks already in the JWT sheet. Wings’ lint can verify each check exists in the callback handler.

4. Initiation and injection (§3.11.1, §4.10).

The RP starts the transaction, and the request carries a nonce.
Prohibit unsolicited IdP-initiated logins.
Bind the callback to the unauthenticated session with an unguessable value (state/nonce).
The RP authenticates to the IdP on the back channel.
Reject callbacks that arrive outside the right stage.

These are required at FAL2+ and recommended at FAL1. Wings should treat them as the default for every app, since they cost little.

4. Presentation (§4.11).

Back channel preferred. The authorization code must be single-use, bound to one RP, unguessable, and valid no more than 5 minutes. The RP authenticates when redeeming it. The IdP verifies the redeemer is the same RP that started the request.
Front channel discouraged. Every flow that returns tokens in the URL is out. This matches the “Auth Code + PKCE only” rule already drafted. Where an IdP uses redirects, personal data in the assertion must be encrypted.

5. Session independence (§4.7).

The assertion’s validity window must not be used to limit the RP session.
Failing to reach an identity API must not extend or end a session.
The RP can ask the IdP for fresh authentication, and the assertion reports when the last authentication happened.
This supports a max_age / step-up rule for sensitive FNs, so the per-FN authorization line should carry an “auth recency” field.

6. FAL levels. FAL1 is basic. FAL2 requires RP-initiated flow, single audience, pre-established trust and injection protection. FAL3 adds holder-of-key or a bound authenticator. A consumer SaaS lands at FAL1–2. I’d put FAL2 behaviour in core as the default and keep FAL3 out, as a regulated-stakes pack.

Wings as its own attack surface

Wings reads upstream repos in full and rewrites them, so those repos are untrusted input to the build step. The rules below come from Secure_Coding_with_AI, AI_Agent_Security, and the earlier gstack/Addy material:

Upstream and fetched text is data, never instructions. The core skill carries one shared statement of this.
Invisible-character scan over generated code and over ingested upstream text: bidi controls (U+202A–202E, U+2066–2069), zero-width characters (U+200B–200D, U+FEFF), and tag characters (U+E0000–E007F). It’s stdlib-only and script-shaped.
Test independence. The agent that writes code shouldn’t be the sole author of its tests. Derive security tests from the spec: the authorization matrix from FN lines, acceptance criteria written before code, RED recorded. A mechanical gate fails any deleted test, reduced assertion count, or newly mocked unit under test. A fresh-context reviewer backs this up.
Scope gate. Each task declares allowed paths (the oma idea). Edits outside them, or to lockfiles, CI, Dockerfiles, package scripts, or rules files, stop for sign-off.
Dependency admission. Every new dependency gets a log entry: exists on the registry, age, maintenance, license, and a lockfile commit.
Autonomy boundary. Reversible local edits are autonomous. Anything destructive or irreversible (production migrations, deploys, secret changes, rules-file edits) needs explicit human approval, and no gate is weakened by the agent that owns the work.

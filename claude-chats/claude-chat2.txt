1. Skill format (Batch 0): the constraints everything else inherits

Hard rules from the spec:

Frontmatter: name (1-64 chars, lowercase, hyphens, must match the directory), description (≤1024 chars), plus optional license, compatibility, metadata, allowed-tools.
Addy’s validator rejects any other top-level key.
SKILL.md stays under 500 lines and about 5,000 tokens. Detail goes in references/ one level deep, with explicit load triggers.
Descriptions say what the skill does and when to use it. Addy adds: don’t summarize the workflow in the description, or the agent follows the summary and skips the body.

Style rules from best-practices and skill-anatomy:

Add what the agent lacks. Cut what it already knows.
Provide defaults, not menus.
Procedures over declarations.
Gotchas sections are the highest-value content.
Prescriptive only where the task is fragile.
Write the procedure, not the model-specific workaround.

Decision: adopt Addy’s section anatomy. The agentskills spec leaves the body free-form. Addy’s Overview / When to Use / Process / Common Rationalizations / Red Flags / Verification is the most distinctive thing in this corpus. Ideas worth carrying, by source

spec-kit

Phase structure of tasks.md. Setup → Foundational (blocking) → one phase per user story in priority order → Polish. Each story is independently testable. Strict task line format - [ ] T001 [P] [US1] description with path. This is the single most reusable artifact for your “agent opens one file and knows what to do” goal.
Spec rules. Max 3 [NEEDS CLARIFICATION] markers, made-up defaults recorded under Assumptions, success criteria technology-agnostic and measurable.
Clarify. Ten-category ambiguity scan, max 5 questions, one at a time, each with a recommended answer, answers written into the spec immediately. Question-quality rule: a label like “Acceptance device matrix (FR-023)” is not a question.
Checklist as unit tests for English. It tests requirement quality, not implementation. [x] is reviewer-owned and never self-ticked by the generator.
Analyze. Read-only, stable IDs, coverage table, max 50 findings, constitution violations always CRITICAL.
Converge. Append-only tasks, byte-for-byte unchanged when clean. This closes the loop after implement and is rare.
Contract-driven development. One authoritative owner per contract, consumers pin a version, provider and consumer tests both required. It is directly relevant to your gap #2 (per-function backend contracts).
Constitution. Versioned governance with a sync report and MAJOR/MINOR/PATCH amendment rules.

BMAD

Altitude. Each level states only what the level below would get wrong. Requirement lines are R<n> with a named source.
Single writer per document. Hand edits are overwritten, and changes flow from the PRD outward.
Architecture spine. Only invariants, each with Binds, Prevents and Rule. The test: “if two units built this independently, could they choose incompatibly, and is it non-obvious and a real trade-off?” This is the best decision filter in the corpus.
Reviewer gate. Deterministic lint first, then rubric walker plus lenses as parallel subagents, each writing a file and returning a compact summary. Matches your frontend-block decision.
Lens set. Adversarial (min 10 findings), edge-case path tracer, verification-gap (names the regression a missing test would catch), structure, prose.
bmad-project-context. Admission rules for what goes in AGENTS.md (derivable stuff is excluded) and a retention ledger. A strong model for your project-rules file.

Build skills read the epic and entry, not a pre-written story file, so detail isn’t written months before use.

Addy

interview-me. Hypothesis plus confidence number, one question with a guess attached, “want vs. should-want” probe, restate with Out of scope, explicit yes, stop the turn. The 95% test: can I predict the next three reactions?
spec-driven-development. Six areas (objective, commands, structure, code style, testing, boundaries) with Always/Ask first/Never tiers, plus Phase 0 capability map with stable module ids. This is the “stack-inclusive spec” from your handoff.

ETHOS principles. Honest Work (no self-certification, a gate is never weakened by the agent), Attack the Premise (two fixes sharing a premise means the premise is the bug), Explain the Number, Make Operations Idempotent. These are genuinely good house-mindset material.

Why these files matter

They sit on one dependency chain. How long artifacts live (persisting-specs.md) constrains the ID rules, the ID rules constrain the linters, and the linters and gstack’s gates define what “done” means. So I analyze them in that order.

1. Artifact lifecycle (persisting-specs.md)

Spec Kit offers four models and mandates none: flow-back, flow-forward, living spec, constitution-only.

Recommendation: living spec, with an append-only decision log.

Flow-forward creates a new feature directory per change. That duplicates IDs across directories, which check_ids.py reports as duplicate. It is incompatible with a global ID scheme.
Constitution-only discards feature artifacts. Wings’ whole purpose is that an agent can open one file later and know what a page, function or table must do. It fails that.
Flow-back allows silent drift. That is the failure the linters exist to catch.
Living spec makes spec.md and the per-page, per-function and per-table files the contract. Plan and tasks are disposable derivations. Its stated risk is lost rationale, which the append-only log (section 2, memlog) covers.

Required rule: IDs are never reused or renumbered, and removed items are marked withdrawn rather than deleted. This is exactly what lint_spine.py (monotonic AD ids) and check_ids.py (withdrawn but still referenced) enforce, so the rule and the tooling already agree.

2. Mechanical layer
check_ids.py: take it, extend it

It is stdlib-only, deterministic and JSON-out, which fits your “no heavy runtimes” rule. Its definition rules are carefully built:

Definitions are headings, first table cells, bold, or - FR-3: list items. Id lists and ranges are references.
A table that mostly re-cites already-defined ids is treated as a traceability table.
Fenced code and HTML comments are blanked with line numbers preserved.
It also checks the Table of Contents against GitHub anchors.

Constraints and gaps that affect the wings design:

Issue	Consequence
Id pattern is [A-Z][A-Z0-9]{0,5}-\d+	The house scheme must be hyphen plus number: R-12, PG-3, FN-7, TB-2, AD-4. My earlier R<n> form would not match. Readability is recovered by always titling the heading (## FN-7 createInvoice).
Anything shaped like an id matches	SHA-256, UTF-8 and ISO-8601 land in unknown_prefix. Add --prefixes so wings checks only the prefixes it owns.
Table heuristic depends on order	A traceability table written before the definitions would define the ids and then collide with them. Rule: define first, trace after.
withdrawn only reads text right after the defining id	Add a check for superseded by X and that X exists.
Counts only, no relationships	It cannot say “every R-n has a task and a test”, “every FN cites an R”, or “every TB is used by an FN”. Wings needs typed coverage rules. The defined and referenced maps already hold the data, so this is an extension, not a rewrite.
Always exits 0 on findings (lint_spine too)	Add --strict for gate use.
No --help	using-scripts.mdx makes it the agent’s primary interface. Add argparse.
lint_spine.py: merge into the same tool
The blank_fences trick (blank, keep newlines) is worth reusing as-is.
The version-pin check finds Name and Version columns from the header row, so reordered tables still work. This maps directly onto the stack decision record, which no source covers.
Weakness: the Binds/Prevents/Rule check is a substring test on the lowercased block, so “rules” or “overrule” satisfies “rule”. Require the fields as labeled lines (**Rule:**).
Drop the convention that the spine must be named after its folder. It is arbitrary.
Result: one wings-lint with modules: ids, placeholders, version pins, required fields per document type.
memlog.py: keep the idea, drop the script

Its three invariants are good:

Entries are append-only and chronological.
It is write-only and blind (each command echoes state, so the caller never re-reads).
It has no lifecycle status. “Done” or “blocked” is itself an entry, so the chronology stays the single source of truth.

It requires PyYAML plus uv, which breaks the no-dependency rule, and nothing it does needs a script. An agent can append - (decision) … lines to a file. Wings should adopt the format: a .wings/log.md with typed one-line entries (decision, assumption, gap, event). It serves as the rationale record the living-spec model needs and as the resume point for a fresh session.

Contrast with gstack’s decision ledger: it uses mutable records with State/Actual answer/Accepted scope fields. Pick the append-only log for working memory.

Structure models map cleanly onto wings artifacts:
Per-page, function and table files: Reference/Database (consistent schema, MECE, random access).

5. Testing (testing-patterns.md, gstack tests.md)

Take from testing-patterns.md:

Arrange-Act-Assert.
Names as [unit] [behavior] [condition].
Mock at boundaries only (DB, HTTP, filesystem, external APIs, time). Never mock business logic, validation or pure functions.
Query by role and label, not test IDs.
The anti-pattern table.

Problems with it:

It is JS/TS-only. Principles belong in the core skill, and syntax goes in per-stack references loaded by detected stack.
It lists toBeDefined and toBeTruthy as “common assertions”, while gstack’s bootstrap forbids expect(x).toBeDefined() as meaningless. Wings should forbid weak assertions.
Its Playwright example asserts a CSS property (text-decoration-line), which is an implementation detail, and its own anti-pattern table flags that.

Take from gstack tests.md:

Markers are evidence for a question, never a command to run. Never execute a candidate test command “to check it”.
Absent config is not absence of tests. Django keeps tests in <app>/tests.py, Go in *_test.go, Rust in #[test] inside src/.
Never install a second framework next to a working one.
Read two or three existing tests for conventions before writing any.
A lane passes on its test count, not exit 0. Three states: tests_ran: N>0 (pass), 0 (ZERO-RUN, treated as failed), unknown (record it). This is small and prevents a very common false pass.
Test failure ownership triage. Classify each failure as in-branch or pre-existing. When ambiguous, default to in-branch. In-branch failures stop the work. Pre-existing ones get a choice: fix, log, or skip.

Drop from tests.md: the “100% coverage is the goal” mandate. The gstack plan-eng-review file contradicts it. Its test value bar is the better rule, and every proposed test must answer four questions:

What behavior does it protect?
What credible regression makes it fail?
Why does existing coverage not catch that?
Does it need a production seam nothing else uses?

Also take the E2E vs unit decision matrix and the regression iron rule: any change that risks existing behavior needs regression coverage.

Analysis of bmad-ux (SKILL + references)

Licensing: gstack being MIT closes that flag. The notices still need to carry over where text is reused, and the pstack attribution inside plan-eng-review (Lauren Tan, MIT) still needs a NOTICE entry.

Architectural reasoning

bmad-ux is the first source I have read that solves the frontend-to-requirements handoff, which is where wings’ frontend block plugs into the spine. Its core move is splitting UX into two peer contracts with a clean ownership line:

DESIGN.md owns how it looks (tokens, visual rules).
EXPERIENCE.md owns how it works (IA, states, flows, accessibility behavior).
EXPERIENCE.md references DESIGN.md by token name ({colors.primary}), never by value, so each fact has one home.
Both win over any mock, wireframe or import.

That is the same single-owner and single-writer discipline as the architecture spine and the contract rule. It is also the missing piece for your goal that an agent opens one file and knows what a page must do. EXPERIENCE.md is the closest source to your per-page requirement file, though it is product-wide rather than per-page (see gaps).

What to take

1. The two-spine split and the DESIGN.md format.

Frontmatter tokens (colors, typography, rounded, spacing, components) plus a prose body in locked section order (Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do’s and Don’ts).
{path.to.token} references resolve against the YAML structure, so a linter can check them mechanically. This is the same pattern as check_ids.py and belongs in wings-lint.
It is an open spec (Google Labs, Apache-2.0), not BMAD’s. That removes the trademark concern, and it means you can vendor the spec reference directly and keep the Apache notice and a change mark.
Inheritance rule: when Foundation names a UI system (shadcn, MUI, native), the spine specifies only the delta. This matters for you specifically: a UI-inexperienced builder should default to shadcn or a native system rather than invent tokens.
Light/dark either as paired tokens or as separate files, and note: fields for platform-owned values.

2. The EXPERIENCE.md section set. Foundation, Information Architecture, Voice and Tone, Component Patterns (behavioral), State Patterns, Interaction Primitives, Accessibility Floor, Key Flows, plus Inspiration & Anti-patterns and Responsive & Platform when triggered. Invented sections are allowed when they earn their place.

3. Surface closure. The best idea in the set: IA closes only when every stated need has a surface, and every surface has a journey that lands on it. When closure fails, probe; never invent the missing piece. This is a deterministic-enough check to turn into a requirements-to-pages coverage rule.

4. Journeys with a named protagonist and a climax beat. “Mary, mom of three, kids asleep”, not “the user”. Named protagonists also derive the form-factor (Pary on iPad implies an iPad surface), and form-factor must resolve before IA closes.

5. Elicit, never impose. Never volunteer colors or directions. Ask what the stakes are (hobby, internal, consumer, regulated). This conflicts with your stated need: you are not experienced in UI design and want the agent to carry that load. See the conflict below.

6. The rubric walker. Eight categories in two passes, and the pass split is the thing to keep:

Pass 1, mechanical: flow coverage, token completeness, component coverage, state coverage, visual reference coverage. Each is extract, then list misses with locations.
Pass 2, judgment: bloat and overspecification, inheritance discipline, shape fit. Each gets a verdict (strong, adequate, thin, broken).
Severity means downstream impact, not fix difficulty.
Color tokens without hex are critical, because code mirrors the spine.
Pass 1 is script-shaped. Flow coverage and token completeness especially should be a deterministic check, not a prompt.

7. Reviewer gate, opt-in and lens-selectable. The user picks all, some or none because reviewers are costly. This agrees with what I proposed for the other review skills.

8. Artifact handling. Working artifacts go to .working/, and only the ones a future reader of the spine would open are promoted to mockups/ or wireframes/. Default is leave in .working/. Reviewer and renderer subagents return a compact summary only, never the payload.

9. Reconciliation of imports. User-supplied Figma exports, sketches and brand decks are reconciled against the spines and dropped qualitative ideas are surfaced. Spines win on conflict.

10. Headless contract. A closed status set (complete, partial, blocked), with assumptions[] and open_questions[] kept separate: inferences go in one, human-decision gaps in the other. Never invent persona, brand or scope. This is a clean, portable convention for non-interactive runs.

What to drop
The whole runtime. uv run resolve_customization.py, resolve_config.py, memlog.py, customize.toml, and every {workflow.*} placeholder. This is the same portability problem as the BMAD stubs: the skill cannot run without BMAD installed, and its own failure path is “install bmad”. Replace with plain paths and fixed defaults.
The persona and cast layer (John, Mary, Sofia). Names stay out and the ideas stay in.
Party mode, advanced elicitation and the misroute scan. BMAD-internal.
{workflow.external_sources}, design_handoffs, external_handoffs. Org-configured registries. Not needed for a single-user suite.
Creative tools as a registry. The renderer contract is good (subagent writes to .working/ and returns a summary), but wings should hardcode the defaults rather than invent a plugin system: HTML color themes, design directions, wireframes, key-screen mocks.
Browser-opener commands per OS and the HTML validation report. Markdown output is enough, and a UI-inexperienced user is better served by one readable report.
The two-assessment machinery of Impeccable is not here; this source’s checks are all coverage plus rubric, so there is nothing else to strip.

How this changes the plan
The frontend block can now be specified as two layers: a direction and system step that produces DESIGN.md, and a requirements step that produces EXPERIENCE.md plus per-page files. They share the token reference syntax, which wings-lint checks.
wings-lint gains two modules: token-reference resolution against DESIGN.md frontmatter, and surface-closure (needs to pages to journeys).
The review lenses for UX come largely free from the rubric walker; I would keep its eight categories, collapse “visual reference coverage” into a simple orphan-file check, and keep Pass 1 scripted.

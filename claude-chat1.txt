Architecture reasoning

The blocks aren’t independent, so the reading order follows dependencies:

Skill format first. Every block’s output is a skill, so the anatomy, size limits, and description rules constrain everything else.
Requirements and SDLC process next. These are the spine. They define the ID scheme, the gates between phases, and what each phase hands to the next. Frontend, backend, database and security all plug into those gates and IDs.
Database and backend before security. Security rules (RLS, authorization, input validation) attach to tables and functions, so the data and contract shapes must be understood first.
Frontend is largely independent, but it consumes the requirements’ per-page shape and the security rules.
Packaging last. It wraps a finished structure, but I want to read it early enough to avoid designing something unpackageable. Hence it’s batch 5, not 6.

Paths are relative to skills/<owner>/<repo>/ from your tree. Send in batches; I’ll analyze each before the next.

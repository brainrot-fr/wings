# arch-wings.md

## Status
Wings architecture decisions, v1. Kernel design is separate. Items marked OPEN are unresolved.

## D1. Product shape
- Wings is a suite of **sibling skills** plus a router. It is not one monolithic skill.
- Any sibling is installable and usable alone on an existing codebase.
- A skill never requires another skill. Cross-skill use is a soft dependency with a labeled degraded fallback.

## D3. Rule: each fact has one home
Auth is reached from Requirements, Backend, Security and Frontend, but its rules live only in Identity & Access. Other blocks link to it.

## D4. Engineering emphasis
Requirements, Code Review and Testing get the deepest treatment. They are scripted where possible, have the largest reference sets, and get the highest QA bar (eval loop, with and without the skill).

## D5. Dual mode
Every skill that can audit supports two modes.
- **Attached:** `.wings/` exists. The skill reads spine artifacts and cites spine IDs.
- **Standalone:** there is no spec. The skill runs a recon step, which is a surface inventory from the code. Findings cite `file:line` and carry local IDs.
- Recon is a shared fragment, not a separate skill.

## D6. Shared contracts without duplication
- One source file per contract lives in the wings repo.
- A build step inlines **kernel-lite** into every sibling.
- The lint fails on hash drift between the source and any inlined copy.
- Cross-skill soft dependency: Code Review loads Security, Frontend and Testing lenses if installed. Otherwise it runs general lenses and labels the result degraded.

## D7. Size policy
- The 8 KB cap is not required.
- 500 lines and about 5k tokens per `SKILL.md` is a lint warning, not an error.
- Detail goes in `references/`, one level deep, with explicit load triggers.

## D8. Capability blocks (v2, reserved, not designed in v1)
Payments, Email & Notifications, Background Jobs, File Storage, Search, i18n, Privacy & Compliance, LLM Features.
- v1 reserves their ID prefixes and the pack interface (§D9).
- Each needs primary documentation before design. They are not synthesized from memory.

## D9. Stack packs
Optional and stack-conditional, loaded only when the stack record names the stack. Each rule carries `applies_to`, `status`, `verified_at` and `source`. A pack with an expired `verified_at` loads with a re-verify warning.

## D10. Tooling
- `wings-lint` and gates are stdlib-only and have no runtime fetch.
- Browser-bound or CLI-bound checks are optional enhancers with a labeled fallback.
- Build-time tools (rule distillation, comply and eval harness, upstream audit) may use more.
- Packaging is a thin layer over one skills directory. Skills are the portable surface. Commands are optional and generated.

## D11. Provenance and licensing
- Upstream repos are read in full and rewritten into one voice. Nothing is ported as machinery.
- MIT and Apache text is carried with notice.
- CC BY-SA text (OWASP, Trail of Bits) is adapted only in separate credited files with a change notice.
- NIST text is reusable with attribution.
- Normative claims are verified against a primary source before they are written down.

## D12. Source-reliability policy
- Claims carried from earlier reads are not rules until re-checked.
- Hand-computed numbers (contrast ratios) are generated by script, never typed.
- Unsourced thresholds are labeled "wings judgment".
